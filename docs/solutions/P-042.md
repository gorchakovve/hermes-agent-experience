# P-042. Агент обещал выполнить действие без доказательства

**English:** [P-042](en/P-042.md)

## Статус
**Подтверждено для Talos/OpenClaw на 2026-06-15.** Runtime guard включён в enforce-режиме только перед финализацией ответа. Hook отправки сообщений оставлен в observe-only из-за отсутствия стабильного run/session identifier.

## Условия
- Дата: 2026-06-15.
- Контур: Talos/OpenClaw, ответы в Telegram и агентских каналах, promise guard.
- Участники: модель формирует финал; guard проверяет наличие обещания и receipt; delivery pipeline отправляет уже финальный текст.

## Симптомы
Агент мог отвечать «сделаю», «продолжаю», «пришлю» без запуска инструмента, создания файла, handoff'а или другого проверяемого результата в том же ходе.

## Причина / гипотеза
Prompt-правило не даёт гарантии. Нужен runtime gate: если в финальном ответе есть обещание работы, но нет receipt текущего хода, финал должен быть заменён честным blocker. Перехват на `message_sending` признали небезопасным, потому что на этом уровне не было стабильной связи с конкретным run/session.

## Неудачная последовательность
1. Пользователь просит выполнить действие.
2. Модель обещает сделать его позже.
3. Инструмент или другое действие не вызывается.
4. Пользователь получает видимость прогресса без артефакта.

## Успешная последовательность
1. Guard анализирует финальный ответ перед отправкой.
2. Если найдено обещание и `receipts=0`, он требует revise.
3. Финал заменяется на честный `[BLOCKED]` или объяснение, что работа ещё не запущена, с конкретным следующим шагом.
4. `message_sending` продолжает логировать и наблюдать, но не блокирует доставку.

## Проверка результата
Контролируемый no-deliver тест вернул признаки `promise=true`, `receipts=0`, `wouldRevise=true`; финальный ответ был переписан в честный blocker. Отдельные smoke-проверки показали, что обещание с реальным receipt не блокируется, а gateway остаётся active.

## Ограничения
- Проверка доказывает поведение конкретного guard, а не семантическую истинность любого receipt.
- Это не доказательство доставки во всех Telegram-топиках.
- Guard не менял модель, прокси, Telegram delivery plugin или архитектуру OpenClaw.

## Связанные случаи
- [P-041](P-041.md) — межагентная работа тоже должна иметь ack/resolve/close receipt.
- [P-043](P-043.md) — отдельный сбой: silent `NO_REPLY` мог подавить доставку даже после guard revise.

## Уверенность доказательств
**Высокая.** Есть датированные внутренние receipts по rollout, controlled no-deliver подтверждение, observe smoke-проверки и решению не включать небезопасный message_sending enforcement.
