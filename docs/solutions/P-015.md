# P-015. Несколько клиентов конкурировали за Codex OAuth refresh token

**English:** [P-015](en/P-015.md)

**Статус:** подтверждённый эксплуатационный вывод. Позднейший ремонт отдельной Hermes credential подтвердил восстановление для Hermes, но не доказывает общее продуктовое ограничение «один человек — один клиент».

## Когда и при каких условиях
С мая по сентябрь 2026 несколько агентских runtimes и клиентов могли использовать одну ChatGPT/Codex OAuth identity. Codex OAuth использует вращаемые refresh tokens, а независимые процессы не имели общего владельца токена с блокировкой.

## Симптомы
В auth state появлялись `refresh_token_reused` и `relogin_required`. Позже удалённый Desktop-клиент видел HTTP 401 из-за истёкшего или терминально недействительного токена. Ошибка выглядела как «авторизация внезапно сломалась», хотя сеть и tunnel могли быть исправны.

## Причина
Подтверждённая причина этого класса отказов: несколько несинхронизированных клиентов использовали один rotating refresh-token state. Один клиент мог обновить токен, а другой — попытаться использовать уже потреблённый старый токен и получить reuse/replay failure. Конкретный процесс, виновный в каждом refresh, не установлен, но локальные признаки совпадают с публично известным классом гонок.

## Роли агента и пользователя
Пользователь выбирал экономику и распределение провайдеров между агентами. Агент должен был уточнить формулировку: проблема не в том, что один владелец никогда не может использовать Codex в нескольких местах, а в том, что несколько always-on runtimes не должны делить один refresh-token state без синхронизации.

## Что не помогало или было рискованно
- Копировать OAuth-файлы между клиентами.
- Запускать автоматические device-login/refresh loops.
- Считать Desktop/tunnel причиной 401 без проверки auth state.
- Делать новый вход для нескольких агентов в один и тот же state.

## Что сработало
1. Назначить одного владельца для конкретной Codex OAuth credential.
2. Другие агенты перевести на отдельный аккаунт/route/API-key/fallback с лимитами.
3. Делать OAuth login только интерактивно и только для выбранного владельца.
4. Удалить proven-invalid credential, чтобы она не выбиралась снова.
5. Проверить живой model smoke и отсутствие новых 401/reuse в свежих логах.

## Проверка результата
В сентябрьском ремонте Hermes получил новую credential, принадлежащую только Hermes. Два live sentinels вернулись успешно; после smoke в проверенном журнале не появилось новых `401`, `token_expired`, `refresh_token_reused` или terminal-invalid ошибок. Desktop remote path также подтвердил готовность backend.

## Ограничения
Не доказано, что OpenAI запрещает одному человеку несколько клиентов. Также не доказано, что upstream никогда не исправит locking/persistence. Правило относится к этому стеку: один rotating OAuth state — один активный владелец или общий token service с locking.

## Основание и уверенность
Основание: decision note о Codex OAuth contention от 2026-05-31 и maintenance receipt Hermes Desktop/Codex OAuth repair от 2026-09-24. Уверенность: высокая для этого failure mode и восстановления Hermes; средняя для причинности каждого отдельного refresh.
