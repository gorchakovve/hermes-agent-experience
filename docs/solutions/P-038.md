# P-038. Передача Hermes → OpenClaw могла потерять результат при отказе runner

[English](en/P-038.md) · [Индекс](../problem-index.md)

**Статус:** частично подтверждено: runner стал записывать blocked-result при сбое, но post-change end-to-end отказ не был отдельно воспроизведён.

## Условия и симптомы

12 июня 2026 года обновление Talos/OpenClaw завершилось успешно, оба gateway были active, но последующая orchestration-задача через runner стала медленной и непрозрачной. В follow-up вызове Talos task runner использовал Gemini Flash и упёрся в free-tier quota 429; при этом result-файл не создавался. Для наблюдателя это выглядело как потерянная задача.

## Причина и проверяемая гипотеза

Причина была не в самом обновлении OpenClaw. Проблема находилась в orchestration layer: при отказе модели или CLI runner не материализовал failure как результат. Гипотеза: каждый сбой агента должен завершать task state явным `status: blocked` или `status: error`, а не молчаливым отсутствием файла.

Общий шаблон для runner:

```sh
if agent_call_fails; then
  write_result status=blocked reason="model_or_quota_failure"
fi
```

## Что помогло и что проваливалось

Помогло остановить только застрявший старый runner, не перезапуская здоровые gateway, затем изменить runner так, чтобы failed OpenClaw calls писали blocked result. Также добавили параметр модели `TALOS_TASK_MODEL`, сохранив старый default.

Проваливалось молчаливое ожидание: отсутствие result-файла превращало понятный quota-отказ в неопределённое зависание orchestration.

## Проверка и ограничения

Запись сообщает: `bash -n` runner script OK; Hermes и OpenClaw gateway active; после cleanup не осталось активных runner/agent/update процессов. Ограничение: сама запись не содержит отдельного post-change end-to-end теста, где специально провоцируется отказ и затем читается новый blocked result. Поэтому статус остаётся частичным.

## Основание

Внутренняя maintenance-запись «Hermes/Talos Runner Optimization» от 2026-06-12. Полные runner paths, task IDs и сырые логи не публикуются.
