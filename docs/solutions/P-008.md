# P-008. Hermes CLI отвечал, затем падал с кодом 134

**Статус:** открыто; подтверждён как известный риск runtime/transport; точное исправление в коде в первичных Brain-записях не найдено.

**Основание:** MAINTENANCE-записи 2026-06-20/21; другие агенты зафиксировали полезный вывод с маркером CLI_FAILED/134/core-dump и последующую локализацию как transport warning при meaningful stdout. Сырые журналы, приватные пути, токены, домены и адреса не публикуются.

**EN:** [`P-008.md`](en/P-008.md)

## Симптомы
CLI/runner успевал записать полезный ответ, но транспорт завершался ошибкой 134 или rc=-6 с core-dump/cleanup tail.

## Условия и время
Наблюдалось в контексте interagent/runner примерно 2026-06-20/21. Отдельный исходный кейс с safe mode и Honcho memory provider в доступных Brain-файлах не найден.

## Гипотеза / причина
Часть, подтверждённая evidence: это сбой cleanup/transport после useful output, а не обязательно сбой полезной работы. Неподтверждённая часть из прежнего черновика — конкретная причина “двойной shutdown memory provider”; найденного первичного основания для неё нет.

## Что сработало
В слое interagent такой исход стали трактовать как ok with transport_warning, если stdout был meaningful, чтобы не терять полезный результат. Отдельный runtime bug всё равно оставлен как known state, который надо расследовать на стороне upstream/runtime.

## Проверка результата
Дополнительные smoke-проверки interagent после rollout дошли до closed; очистка предупреждений убрала unrelated unknown toolset warning.

## Ограничения
Не заявлять py_compile/три direct smoke/safe-mode/Honcho root cause как факт без отдельного источника. При повторе сохраняйте stdout/stderr separation: если output meaningful, верните результат с transport warning; если output пустой, считайте это failure.
