# P-044. Telegram macOS не поддерживал rich-ответы OpenClaw

**English:** [P-044](en/P-044.md)

## Статус
**Частично подтверждено на 2026-06-17.** Первое plain-send исправление для Talos/OpenClaw было применено, серверные smoke-проверки прошли, но последующие случаи показали, что покрыты не все Telegram rich-пути.

## Условия
- Дата: 2026-06-17.
- Контур: Talos/OpenClaw → Telegram macOS.
- Участники: Telegram client отображает payload; OpenClaw Telegram adapter формирует Bot API payload; модель только генерирует текст.

## Симптомы
На iMac в Telegram появлялись блоки unsupported message и кнопка обновления, хотя текст ответа мог быть видимым. Клиент Telegram был актуальным, поэтому повторное обновление приложения не объясняло проблему.

## Причина / гипотеза
Первая заплатка prompt capabilities убрала richText из подсказки модели, но фактический delivery path всё ещё мог использовать Bot API rich-message для обычных текстовых chunk'ов и reply/quote payload. Значит, проблема была в серверной форме payload, а не в устаревшем Telegram-клиенте.

## Неудачная последовательность
1. Модель генерирует обычный текст.
2. Prompt capabilities уже выглядят как plain-text-only.
3. Delivery adapter всё равно отправляет rich/reply/quote payload.
4. Telegram macOS показывает unsupported block.

## Успешная последовательность
1. Сначала подтвердить, что клиент актуален, чтобы не чинить не ту сторону.
2. Сделать backup runtime-файлов.
3. Перевести текстовые Telegram chunks OpenClaw/Talos на plain `sendMessage`.
4. Сохранить forum topic/thread id, но убрать rich payload, inline reply markup и quote/reply параметры из фактической отправки текста.
5. Закрепить исправление в post-update helper.
6. Проверить syntax/config, перезапустить только OpenClaw gateway и выполнить реальные send smoke-проверки.

## Проверка результата
Node syntax и config validate прошли. Gateway был active. Две реальные отправки в topic логировались как plain text send с сохранённым thread id. Post-update helper сообщил, что plain-text delivery уже применён.

## Ограничения
- Это исправление не доказало отсутствие unsupported block на каждом клиенте.
- 2026-06-18 проблема воспроизвелась шире, включая Hermes и дополнительные пути edit/preview; см. [P-047](P-047.md).
- Сырые bundle names и внутренние пути не являются стабильными API и здесь не публикуются.

## Связанные случаи
- [P-045](P-045.md) — progress draft cards шли отдельным rich path.
- [P-047](P-047.md) — последующее двустороннее исправление для Hermes/Talos.

## Уверенность доказательств
**Средне-высокая для первого исправления, средняя для полного закрытия.** Серверные smoke-проверки подтверждены, но полное клиентское визуальное подтверждение и покрытие всех путей появились только в следующих случаях.
