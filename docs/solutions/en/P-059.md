# P-059. Chromium did not load `file://` PAC; Gemini also needed routing for static assets

[Русская версия](../P-059.md)

**Evidence status:** Verified by a 2026-09-24 receipt and user confirmation. The fix had two steps; it should not be reduced to only the `file://` PAC issue.

## Time and conditions
2026-09-24, after the first iMac routing repair.

## Symptoms
Gemini loaded as a blank/partially styled screen; HTTP 200 to the app shell did not mean working chat.

## Observations vs actions
The operator first changed only PAC delivery to a loopback HTTP server serving the byte-identical PAC; then investigated static assets and compared direct VPN route with proxy route.

## Causal hypothesis
There were two causes: Chromium did not accept the needed `file://` PAC, and some static asset hosts were outside the selective proxy route.

## What would not have helped
Stopping at HTTP 200 for the app shell was premature; broadly proxying all Google hosts was unnecessary.

## What helped
A loopback HTTP PAC server, updated Wi‑Fi PAC URL, and adding only observed asset hosts to PAC/sing-box rules helped.

## Result check
The served PAC matched byte-for-byte; the main script through SOCKS returned HTTP 200; the control chat returned a working response; the operator confirmed the normal Chrome interface and replies.

## Limits
The HTTP PAC server became a new local point of failure; VPS/VPN containers were not changed; indefinite availability was not proven.
