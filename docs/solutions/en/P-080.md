# P-080. The first web panel had to be separately protected

**Status:** confirmed for the May repair. The direct default-host/direct-address path no longer returned the dashboard, while intended hostnames stayed behind Access; this does not prove absolute security for all future routes.

**Русская версия:** [P-080](../P-080.md)

## Timeframe and conditions
2026-05-24. The check covered Hermes/Talos/OpenClaw web panels on the VPS, the external access boundary, SSH posture, firewall and reverse-proxy default host.

## Symptoms
The normal hostnames were protected by the external Access boundary, but a direct HTTPS request to the server through the default host returned Hermes Dashboard HTML with private session content. That bypassed the expected hostname-based access check.

## Confirmed cause vs hypothesis
Confirmed: the problem was not absence of Access on the intended hostnames; it was an alternate default-host/direct route that bypassed the hostname boundary. Separately, permissive SSH settings were identified and corrected.

Hypothesis to avoid: “if the domain is behind Access, everything is protected.” Direct and alternate routes must be tested.

## Actor attribution and actions
The operator first reconciled canonical records and Access policy, then performed two repairs: hardened SSH to key-only/no root/password login, and locked down the reverse-proxy default host so unknown HTTP/HTTPS hostnames would not serve the panel. Required named routes were kept working.

What worked: deny/default-host lockdown plus named-domain verification. What was not done: closing all 80/443 traffic, because those ports were needed for hostname routing; the existing VPN/transport port was not broken.

## Practical verification
Check both directions:

```sh
curl -I https://<protected-hostname>/
curl -k -I https://<server-direct-address>/
ssh -o PreferredAuthentications=password -o PubkeyAuthentication=no <host>
```

Expected: hostname goes to Access/login or another approved auth boundary; direct/default host does not return the dashboard; password SSH fails; key SSH remains working.

## Proof of result
After the fix, protected hostnames returned an Access redirect and direct HTTP/HTTPS no longer returned dashboard content. The check also confirmed that the intended administrative login still worked and the insecure login method was blocked. These are results from the repair date, not a claim about the current perimeter.

## Limits and open items
A complete independent external scan of every bypass vector was not claimed; the proven result is the May default-host/direct-address repair. Current external reachability and protective controls need separate verification.

## Lesson
Panel protection is not only “domain behind Access.” Check the default vhost, direct address, exposed service ports, SSH posture and preservation of intended named routes after lockdown.
