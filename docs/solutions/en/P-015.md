# P-015. Multiple clients competed for a Codex OAuth refresh token

**Русский:** [P-015](../P-015.md)

**Status:** confirmed operational finding. A later dedicated Hermes credential repair verified Hermes recovery, but it does not prove a broad product rule that one human may use only one client.

## Timing and conditions
From May through September 2026, multiple agent runtimes and clients were candidates to use the same ChatGPT/Codex OAuth identity. Codex OAuth uses rotating refresh tokens, and the independent processes did not share a locked token owner.

## Symptoms
Auth state showed `refresh_token_reused` and `relogin_required`. Later, a remote Desktop client saw HTTP 401 because the token was expired or terminally invalid. The error looked like “auth suddenly broke,” even though the network and tunnel could be healthy.

## Cause
Confirmed class of cause: several unsynchronized clients shared one rotating refresh-token state. One client could refresh and consume the token while another tried to use the stale token and triggered reuse/replay failure. The exact process responsible for each refresh was not identified, but local evidence matches the known race class.

## Agent/user distinction
The user was deciding provider economics and agent routing. The agent had to state the narrower rule: the issue is not that one owner can never use Codex in multiple places; it is that multiple always-on runtimes should not share one refresh-token state without synchronization.

## What did not help or was risky
- Copying OAuth files between clients.
- Running automatic device-login or refresh loops.
- Blaming Desktop/tunnel for 401 before checking auth state.
- Logging several agents into the same credential state again.

## What worked
1. Assign a single owner for a specific Codex OAuth credential.
2. Move other agents to a separate account, route, API-key path, or limited fallback.
3. Perform OAuth login only interactively and only for the chosen owner.
4. Remove proven-invalid credentials so they cannot be selected later.
5. Verify with live model smokes and absence of fresh 401/reuse errors in new logs.

## Verification
In the September repair, Hermes received a fresh credential owned only by Hermes. Two live sentinels returned successfully; after the smoke, checked logs showed no fresh `401`, `token_expired`, `refresh_token_reused`, or terminal-invalid errors. The Desktop remote path also confirmed backend readiness.

## Limits
This does not prove OpenAI forbids one human from using multiple clients. It also does not prove upstream will never fix locking/persistence. The rule for this stack is: one rotating OAuth state needs one active owner, or a shared token service with locking.

## Evidence and confidence
Evidence: 2026-05-31 Codex OAuth contention decision note and 2026-09-24 Hermes Desktop/Codex OAuth repair receipt. Confidence: high for this failure mode and Hermes recovery; medium for causality of each individual refresh.
