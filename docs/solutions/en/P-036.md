# P-036. External-access documentation diverged from live configuration

[Русский](../P-036.md) · [Index](../../problem-index.en.md)

**Status:** verified for the May check: the direct fallback route was closed, and normal named routes stayed behind external authorization.

## Conditions and symptoms

Documentation described the agent dashboards as protected by an external access perimeter. The 24 May 2026 audit checked not only named routes but also a direct/default route to the server. SSH settings were also broader than desired. The risk was documentation promising protection while a live server still served a dashboard through a route that bypassed the access layer.

## Cause and testable hypothesis

The cause was drift between canon and live network/service configuration. The hypothesis to test: named hostnames can be protected while a direct default host or fallback route still exposes the panel.

Generic safe sequence:

```sh
# Check the normal hostname: it should require external authorization.
# Check the direct/default route: it must not serve the dashboard.
# Check SSH policy and firewall separately from the reverse proxy.
```

## What helped

After backup, SSH login methods were narrowed and the server's fallback web route was closed without breaking the normal named sites. The important check was the negative case: “the panel is not reachable directly,” not just “the service is active.”

## Validation and limits

The record says key-based login still worked after the change, the direct request no longer served the panel, normal domain routes required authorization, and services stayed active. Limit: one client-route check is not an independent external pentest and does not guarantee future configuration changes.

## Evidence

Internal May storage/updater audit-fix and hardening records dated 24 May 2026. Private addresses, domains, SSH paths and raw logs are omitted.
