# P-071. Phone Google AI required a separate proxy exit

**Status:** partially confirmed. The server-side route was installed and synthetic probes passed, but native Gemini/NotebookLM operation on both phones was not accepted as fully proven.

**Русская версия:** [P-071](../P-071.md)

## Timeframe and conditions
2026-09-24. The task involved two phones using existing VPN profiles. Existing keys, the iMac route, the main agent proxy and ordinary internet traffic had to remain unchanged; replacing the whole VPN exit just for Google AI was out of scope.

## Symptoms
Through the ordinary phone exit, Google AI behaved as regionally unavailable. NotebookLM did not reach a usable signed-in state, and simple Google HTTP responses were not enough to prove that the mobile apps would work.

## Confirmed cause vs hypothesis
Confirmed: the selected phone peers did not have a dedicated selective Google AI route through an accepted exit; they were still using the ordinary regional path. The first isolated transparent-routing test also confirmed a reverse-path-validation issue that required careful policy-route exceptions.

Hypothesis: some failures were caused by Google's regional classification rather than account or app failure. That hypothesis was not fully proven on each physical phone.

## Actor attribution and actions
The operator deployed a separate mobile routing service inside the VPN network namespace, without restarting the main agent proxy or changing existing keys. Only two phone sources and a narrow Google AI hostname set were included; iMac and Lenovo were excluded. All other traffic stayed on the existing path.

What failed first: the isolated transparent test hit reverse-path validation without additional throw routes. What worked: a separate policy table for marked Google AI traffic, hostname sniffing without TLS interception, QUIC/UDP handling, and a stop handler that removes only the new mobile-routing rules.

## Practical verification
A safe check should separate three levels:

```sh
sudo systemctl status <mobile-google-routing-service>
sudo systemctl stop <mobile-google-routing-service>
sudo systemctl start <mobile-google-routing-service>
```

1. The service is active, and stop/start does not leave stale policy rules or chains.
2. A synthetic client in a test namespace reaches Google login or app endpoints without the previous regional redirect.
3. A real phone using the same VPN profile opens Gemini/NotebookLM and receives an actual signed-in response, not only HTTP 200.

## Proof of result
The record confirms that the synthetic transparent path worked, NotebookLM reached Google sign-in instead of the previous regional redirect, the Gemini app endpoint returned HTTP 200, DNS/UDP responded, the service was active/enabled, phone handshakes were fresh, the test namespace was removed, and original VPN peers/main proxy were not changed.

## Limits and open items
Not confirmed: a full native Gemini response and signed-in NotebookLM usage on both phones. This case must not be presented as a fully accepted mobile integration. HTTP 200, a login page and a fresh VPN handshake are not app-level proof.

## Lesson
Mobile Google AI routing needs more than “Google works from the server.” Use peer-specific scope, narrow host rules, rollback that does not disturb the main VPN, a synthetic probe, and a required user-facing mobile smoke test.
