# P-073. A live Hermes backend did not prove Windows Desktop was working

**Status:** a separate Lenovo/Windows Desktop lesson is confirmed: backend health alone does not prove the desktop client is connected; the local tunnel/task/UI must be checked.

**Русская версия:** [P-073](../P-073.md)

## Timeframe and conditions
2026-09-27. Lenovo Windows 11 running Hermes Desktop connected to the VPS backend through a local loopback SSH forward. VPN had to remain connected; Task Scheduler history did not reveal why the tunnel task stopped.

## Symptoms
The backend could remain healthy while Desktop lost connectivity because the local Windows task/tunnel had exited. To the user this looks like a broken desktop client, not necessarily a failed Hermes server.

## Confirmed cause vs hypothesis
Confirmed: Desktop stayed open when the Windows tunnel task exited with an interruption code; restarting that task restored the local listener and backend connection.

Not confirmed: the exact cause of the task exit. Because scheduler history was disabled, the incident cannot honestly be attributed to VPN, antivirus or Hermes Desktop itself.

## Actor attribution and actions
Diagnostics separated four layers: VPS backend, local SSH forward, Windows scheduled task/PowerShell parent and Desktop UI. The accepted repair used one trigger at Windows logon and one long-lived PowerShell parent that runs one SSH child with keepalives and restarts that child after exit.

What did not work as a design: a repeating every-minute trigger. It was removed at the user's request to avoid competing watchdogs and duplicate tunnel processes.

## Practical verification
Do not treat `backend /health OK` as a sufficient Desktop test. Check locally:

```powershell
Get-ScheduledTask -TaskName <desktop-tunnel-task>
Get-NetTCPConnection -LocalAddress 127.0.0.1 -LocalPort <local-port>
```

Then run a Desktop UI smoke: backend connection, chat/panel opens, no connection error. To test the watchdog, terminate only the SSH child and confirm that a new listener appears and the backend responds again through the local port.

## Proof of result
The record confirms that after a forced SSH-child exit a new listener appeared, the backend response through the local forward became healthy, and Desktop connectivity recovered. The extra every-minute trigger was removed; the accepted shape is one logon task plus an internal restart loop.

## Limits and open items
The original task-exit cause is unproven. The next incident should start with live task/process/listener state and, if possible, enabled scheduler history. Backend update and Desktop client update are different targets; identify the target before clicking update.

## Lesson
Remote-backend Desktop architecture has at least two live objects: the server and the local bridge. Server health does not replace Desktop UI smoke and local tunnel-supervisor checks.
