# P-014. An agent self-restart interrupted the current answer

**Русский:** [P-014](../P-014.md)

**Status:** open; the incident cause is confirmed, but a permanent runtime fix specifically preventing self-restart mid-turn is not proven. An operational rule reduces the risk.

## Timing and conditions
On 2026-06-20 the agent was handling a Telegram task and initiated a restart of its own gateway while the task was still in progress. Telegram rich/progress-message compatibility fixes were happening in the same area, so some symptoms belonged to message format and some to process interruption.

## Symptoms
The current Telegram answer was cut off. After restart, the agent itself reported it had been interrupted by a gateway restart. Logs recorded several gateway restarts in under two minutes, including one triggered by the agent’s own tool call.

## Cause or testable hypothesis
Confirmed: the gateway process restarted during answer/tool-progress delivery. That is sufficient to explain the interrupted turn. A separate Telegram progress/rich-card issue was fixed in the same maintenance window, but that does not fully protect against any future self-restart.

## Agent/user distinction
The user saw an interrupted or unsupported message. The agent was both the repair executor and the process being restarted. Therefore the usual “restart after patch” habit was dangerous: it killed the channel through which the agent was reporting progress.

## What did not help or was risky
- Restarting the gateway inside a tool call before finishing the answer.
- Treating `changed=none` from an older repair script as proof of full coverage: it did not cover separate progress/draft paths.
- Mixing the Telegram message-format problem with the process-interruption problem.

## What partially worked
Additional Telegram rich/progress call sites were closed and the repair script was proven idempotent. For self-restart, the new rule is: apply changes with `--no-restart`, finish the user-facing response, then perform a separate restart step with a warning and only for the affected service.

Safe pattern:

```bash
repair-script --no-restart
# validate syntax/config
# send status and restart warning to the user
systemctl --user restart affected.service
systemctl --user status affected.service --no-pager
```

## Verification
The record confirms the interruption cause from logs and verifies the Telegram rich/progress path fixes: syntax checks passed, the gateway was active after final restart, the Telegram provider reconnected, and remaining Telegram rich call sites were reduced to an unrelated transport.

## Limits
No separate end-to-end test was found proving the agent can never again restart its own gateway mid-turn. Status for self-restart remains “operationally mitigated, not fully closed.”

## Evidence and confidence
Evidence: 2026-06-20 Telegram progress-draft repair receipt and companion no-self-restart lesson. Confidence: high that the specific interruption was caused by restart; medium-low that the risk is permanently eliminated.
