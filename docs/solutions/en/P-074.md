# P-074. A live OpenClaw gateway did not prove the Windows panel worked

**Status:** no targeted Windows repair is confirmed. Available records support gateway/control-UI verification rules, but do not prove a successful Windows client or Windows panel fix.

**Русская версия:** [P-074](../P-074.md)

## Timeframe and conditions
The index was published on 2026-09-27; no direct dated Windows-panel incident was found in the scoped records. Nearby evidence covers the VPS OpenClaw gateway, Control UI, Cloudflare Access and local health checks.

## Symptoms
It is easy to see `gateway live` or a local `/health` response and incorrectly claim that the user-facing Windows panel works. These are different layers: server gateway, public route/auth boundary, browser/desktop client and user-visible UI smoke.

## Confirmed cause vs hypothesis
Confirmed: in prior OpenClaw cases, the health endpoint and service status proved only that the gateway was running. Other records also show that Control UI auth posture depends on the outer access boundary and config version.

Not confirmed: the specific Windows-panel failure, its cause, the Windows client version, network path, or repair result.

## Actor attribution and actions
In the available evidence, operators checked VPS gateway state, service status, local health, auth posture and public perimeter. That was not a targeted Windows-client repair: there is no Windows screenshot, client log, browser smoke or record that the user-facing panel opened on Lenovo/Windows after a fix.

## Practical verification
Minimum honest checklist for this type of case:

```sh
curl -fsS http://127.0.0.1:<gateway-port>/health
```

Then separately on Windows:

```powershell
Test-NetConnection <expected-host> -Port <port>
```

After that, run a UI smoke: page/panel opens, auth boundary is passed, websocket/API calls do not fail, and a small safe UI action works. Server-side `HTTP 200 health` is only the first step.

## Proof of result
There is no result proof for this P item. There is indirect evidence that the gateway could be live and protected, but no proof of a working Windows panel.

## Limits and open items
Needed: exact Windows architecture and client/browser version, network path, client/browser logs, dated test, screenshot or textual UI smoke without private data, and separation of backend, auth and UI failure.

## Lesson
Do not transfer server health checks into client claims. If the problem is “the Windows panel does not work,” proof must happen on Windows and in the UI, not only on the VPS.
