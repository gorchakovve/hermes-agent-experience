# P-018. After updates, distinguish route misconfiguration from a verified smoke

**Русский:** [P-018](../P-018.md)

**Status:** partially confirmed story. The May Codex route was corrected and smoked; the September record confirms a Hermes update, but it is not separate proof of the old Codex route-selection failure.

## Timing and conditions
The story spans a May post-update repair and a September Hermes update. In the earlier period, the primary route/provider naming needed correction. Later, Hermes was updated in a different configuration state, preserving provider/model settings and applying separate network repairs.

## Symptoms
The index-level issue looked like “after an OpenClaw/Hermes update, the system selected the wrong Codex model path.” Available records show several nearby but non-identical facts: an early route failure/fix, plugin/runtime update, and successful smokes on different dates.

## Cause or testable hypothesis
Confirmed part: an incorrect or stale provider/model route can survive an update and requires an explicit smoke of the route believed to be primary. Unconfirmed part: the September update itself does not prove the old Codex route-selection bug recurred.

## Agent/user distinction
The user expects a simple “fixed/not fixed.” The agent must separate dates and artifacts: a May smoke verifies the May fix; a September successful update verifies that gateway and primary response at that time, but not automatically the old hypothesis.

## What did not help or was risky
- Merging several update receipts into one causal story.
- Treating “config migrated unchanged” as proof that a specific provider route works.
- Inferring runtime behavior from plugin version without a live request through the intended provider/model.

## What worked
1. Preserve the provider/model and fallback contract before update.
2. Run an explicit primary-model smoke after update.
3. If the risk is the Codex route, smoke exactly the Codex provider/model, not another primary.
4. Record date, version, and sentinel separately for each stage.

Example safe check:

```bash
hermes config get model.provider model.default
hermes chat -Q --provider EXPECTED_PROVIDER -m EXPECTED_MODEL -q 'Reply exactly: ROUTE_OK'
```

## Verification
The May record confirms a successful smoke after route correction. The September record confirms the update completed, the gateway worked, a model response returned, and provider/fallback config was preserved; but it is not separate verification of the old Codex route if the active primary differed or was checked differently.

## Limits
The status of the phrase “after update it selected the wrong Codex path” remains partial. To close it fully, one record would need: before/after config diff, observed route-selection error, targeted fix, then live Codex smoke.

## Evidence and confidence
Evidence: 2026-05-23/24 post-update repair status, 2026-05-24 Hermes live update note, and 2026-09-16 Hermes VPS update. Confidence: medium for the May fix; low-medium for broad September causality.
