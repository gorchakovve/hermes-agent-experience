# P-020. The fallback chain mixed limits, a bad slug, and incompatible payload

**Русский:** [P-020](../P-020.md)

**Status:** partially confirmed recovery. The primary→OpenRouter fallback was brought to a working state, but OpenAI direct as a general fallback remained unproven because of incompatible payload.

## Timing and conditions
On 2026-04-21 Hermes used a Codex primary and several fallback providers. The primary hit a usage limit; the first OpenRouter fallback initially returned 404, then could hit free-tier 429; the second OpenAI direct fallback returned HTTP 400 on payload inherited from a Codex-style request.

## Symptoms
One incident produced several different errors:
- primary: HTTP 429 rate/usage limit;
- OpenRouter: 404 for an old slug, then 429 for daily quota;
- OpenAI direct: HTTP 400 `Encrypted content is not supported`;
- manual tests sometimes: `api_key must be set`.

## Cause
The causes were different, not one generic “fallback is broken” issue:
1. Codex primary was quota-limited, not necessarily broken.
2. The OpenRouter slug was stale/nonexistent.
3. OpenRouter free route has daily limits.
4. The OpenAI API key worked in a direct test, but Hermes fallback sent an incompatible Codex-style payload.
5. `api_key must be set` belonged to a manual process without service env, not necessarily the gateway.

## Agent/user distinction
The user saw the agent stop responding under limits. The agent had to separate provider runtime, manual shell environment, and payload format instead of changing every key/model at once.

## What did not help or was risky
- Concluding the key was broken from a manual process without env.
- Treating `openrouter/free` as one stable real model: it is a router and the actual model may change.
- Fixing quota, slug, and payload in one large change without intermediate smokes.
- Printing API-key values while checking environment.

## What worked
1. Corrected the `fallback_providers` structure.
2. Replaced the dead OpenRouter slug with a working/free route.
3. Verified that Codex 429 fell through to OpenRouter.
4. Tested OpenAI direct API separately and proved the key worked.
5. Recorded the remaining issue: OpenAI direct in the shared chain needs simplified payload without Codex encrypted/reasoning fields.

Safe check:

```bash
python - <<'PY'
import os
print('OPENAI_API_KEY=SET' if os.getenv('OPENAI_API_KEY') else 'OPENAI_API_KEY=MISSING')
PY
# Check presence, never print the value.
```

## Verification
The record captured a working transition to OpenRouter on Codex 429 and a successful direct OpenAI API response. But end-to-end OpenAI direct fallback inside Hermes still returned HTTP 400, so the chain was only partially restored.

## Limits
OpenRouter free route does not guarantee availability or quality. OpenAI direct needs separate payload adaptation before it can be considered a full fallback for Codex-style conversations.

## Evidence and confidence
Evidence: 2026-04-21 “Codex → OpenRouter → OpenAI fallback hardening” lesson and 2026-04-27 accepted fallback-chain note. Confidence: high for diagnosing individual errors; medium for OpenRouter stability; low for full OpenAI direct fallback readiness without another patch/smoke.
