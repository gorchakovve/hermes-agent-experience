# P-002. Two OpenClaw gateways were competing for one port

**Status:** confirmed by a 2026-05-02 lessons note; applicable only after identifying the live gateway owner.

**Evidence:** Operations lesson from 2026-05-02; direct observations of processes, cgroups, systemd journal, restart counter, and health. Raw logs, private paths, tokens, domains, and addresses are intentionally omitted.

**RU:** [`P-002.md`](../P-002.md)

## Symptoms
Two OpenClaw gateway processes existed at the same time. The old system service repeatedly restarted while a user service was running. The note recorded 1,823 restarts and roughly 896 MB used by the extra process.

## Conditions and timing
Linux VPS, 2026-05-02. A migration from system-level to user-level installation left both the old systemd unit and the new user unit present.

## Hypothesis / root cause
Both services attempted to own the gateway port. The user service bound first, while the system service failed and restarted. The journal showed an mDNS/CIAO conflict rather than necessarily a direct EADDRINUSE, so a simple listener check could look normal.

## Actions that worked
First distinguish the system and user services, their PIDs, and their cgroups; then identify which instance is actually serving requests. In the observed case the user service was the live one, so only the obsolete system service was disabled: `sudo systemctl disable --now openclaw-gateway.service`.

## Verification
The system service became inactive, the user service stayed active, and the local health endpoint of the live gateway returned a live response.

## Limitations
Do not blindly apply “disable the system unit” elsewhere. Another host may legitimately use the system unit. An mDNS-looking journal error does not remove the need to check the port, cgroup, and health endpoint.
