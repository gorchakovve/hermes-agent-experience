# P-062. A `.ru` rule sent the hosting control panel to a broken route

[Русский](../P-062.md) · [Index](../../problem-index.en.md)

**Status:** confirmed narrow fix for the hosting control panel; not evidence of a general `.ru` fix.

## When and conditions
2026-09-24, an iMac using PAC/sing-box with AmneziaVPN enabled. The same work session also tested the German VPS as a possible Gemini/NotebookLM exit.

## Symptoms
In Chromium, the hosting control panel did not use the ordinary VPN path. It matched the `.ru` route, which had no working local exit on the iMac, and failed as a SOCKS connection error. Safari behaved differently, so the symptom was not universal across browsers.

## Cause vs. hypothesis
The cause was confirmed for one host: PAC/sing-box classified the control panel as `.ru` and routed it to a path bound to an unavailable network exit. This does not prove that all `.ru` sites failed in the same way.

## What helped
One narrow exception was added: the specific hosting panel host goes DIRECT, meaning through the already-connected AmneziaVPN and normal VPS exit. Google AI rules, other `.ru` rules, sing-box, and the server were left unchanged.

## Verification
After the change, PAC decisions for Google AI, NotebookLM, account/avatar resources, and other `.ru` destinations stayed unchanged. A fresh control browser opened the real login page. The user then logged in personally; the agent did not receive a password, CAPTCHA, or private account data.

## What is not proven
There was no full authenticated control-panel acceptance test and no blanket `.ru` remediation. Any new Russian-domain failure still needs host-specific PAC decisions before/after and checks across both routes.
