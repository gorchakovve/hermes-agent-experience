# P-037. SSH file sync failed with rc=-13 while hiding the original tar error

[Русский](../P-037.md) · [Index](../../problem-index.en.md)

**Status:** verified in rehearsal/tests: the GNU-only tar flag was omitted for macOS/BSD tar, and the regression test passed.

## Conditions and symptoms

Hermes synchronized files to a workstation over SSH and sometimes reported an error like `tar create failed rc=-13`. That code looked like a local pipe error, but did not explain why the remote tar process closed the stream.

## Cause and testable hypothesis

The primary cause was tar incompatibility: GNU's `--no-overwrite-dir` flag is not supported by BSD tar on macOS. After the remote tar failed, the local side saw a closed pipe and a secondary rc=-13/SIGPIPE. Therefore the diagnostic target is not only the final rc; inspect remote stderr and tar capabilities.

Generic diagnostic step:

```sh
ssh workstation 'tar --version || tar --help | head'
# If the GNU-only flag is absent, do not pass it to remote tar.
```

## What helped and what not to overgeneralize

Feature detection helped: Hermes should pass `--no-overwrite-dir` only when the remote tar supports it. The rehearsal record also says the patch survived a merge rehearsal and the bulk-upload regression test passed.

Do not overgeneralize: every rc=-13 is not necessarily this BSD tar issue. Other pipe closures can produce the same secondary code; read remote stderr first.

## Validation and limits

The 24 May rehearsal record reports py_compile passed, `git diff --check` passed, and `pytest tests/tools/test_ssh_bulk_upload.py` returned 22 passed. A key finding separately states that the BSD tar fix survived. Limit: the rehearsal was not a live update, and the tests cover the specific file-sync path.
