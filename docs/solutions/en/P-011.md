# P-011. HAProxy failed to start because a TCP port was already owned

**Русский:** [P-011](../P-011.md)

**Status:** confirmed result. The repair is verified by the 2026-08-04 operations receipt, but it is safe to reuse only after checking the local port-ownership contract.

## Timing and conditions
The incident happened on a VPS where HAProxy handled the public reverse-proxy/multiplexing path while a separate Telegram MTProto proxy container was supposed to own a dedicated TCP port. Several services were being remediated in the same window, so the symptom initially looked like a broad proxy-layer failure rather than a narrow bind conflict.

## Symptoms
HAProxy would not start or would not remain healthy after restart. The MTProto container was part of the intended design and should not have been stopped just to make HAProxy start. The user experienced degraded public access; the agent saw a listener conflict on one TCP port.

## Cause
Confirmed cause: HAProxy still had an extra listener for a TCP port already assigned to the MTProto container. This was not an MTProto failure and not primarily a firewall issue. Two processes were trying to own the same address/port.

## Agent/user distinction
The user’s requirement was to restore the stack without breaking a working service. The agent’s job was not to “free the port” blindly, but to identify the legitimate owner, take a rollback copy, and remove only the incorrect HAProxy bind.

## What did not help or was risky
- Restarting HAProxy without changing config: the bind conflict remained.
- Stopping MTProto as the “blocking process”: that would break the service that was meant to own the port.
- Editing firewall or containers blindly: that would not remove the incorrect listener and could create secondary outages.

## What worked
1. Compared HAProxy listeners, container-published ports, and the actual socket owner.
2. Saved the config before editing.
3. Removed only the extra HAProxy listener on the conflicting port.
4. Left the main HAProxy listener/multiplexer and MTProto container in their intended roles.
5. Validated HAProxy syntax before reload/restart.

Safe generic checks:

```bash
ss -ltnp
systemctl status haproxy --no-pager
docker ps --format 'table {{.Names}}\t{{.Ports}}'
haproxy -c -f /path/to/haproxy.cfg
```

## Verification
After the incorrect bind was removed, HAProxy was active again, the MTProto proxy remained available on its own port, and the other services in the post-repair check were active. This verifies the specific port-conflict fix, not every aspect of the reverse-proxy design.

## Limits
Do not copy the action “remove the listener” to another host without local inventory. In a different deployment that port may legitimately belong to HAProxy.

## Evidence and confidence
Evidence: 2026-08-04 VPS remediation receipt plus the earlier MTProto proxy operations note. Confidence: high for cause and result; medium for applying the pattern to other HAProxy layouts.
