# P-044. Telegram for macOS did not support OpenClaw rich replies

**Русская версия:** [../P-044.md](../P-044.md)

## Status
**Partially verified as of 2026-06-17.** The first Talos/OpenClaw plain-send repair was applied and server-side smokes passed, but later incidents showed that not all Telegram rich paths were covered.

## Conditions
- Date: 2026-06-17.
- Surface: Talos/OpenClaw → Telegram for macOS.
- Actors: the Telegram client renders the payload; the OpenClaw Telegram adapter builds the Bot API payload; the model only generates text.

## Symptoms
On the iMac, Telegram showed unsupported-message blocks and an update button, even though the reply text could still be visible. The Telegram client was current, so updating the client again did not explain the issue.

## Cause / hypothesis
The first prompt-capabilities patch removed richText from the model prompt, but the actual delivery path could still use Bot API rich-message payloads for normal text chunks and reply/quote context. The problem was therefore the server-side payload shape, not a stale Telegram app.

## Failed sequence
1. The model generates normal text.
2. Prompt capabilities already look plain-text-only.
3. The delivery adapter still sends rich/reply/quote payload.
4. Telegram for macOS shows an unsupported block.

## Successful sequence
1. First confirm the client is current, so the wrong side is not repaired.
2. Back up runtime files.
3. Move OpenClaw/Talos Telegram text chunks to plain `sendMessage`.
4. Preserve the forum topic/thread id, but remove rich payload, inline reply markup, and quote/reply parameters from actual text sends.
5. Put the repair into the post-update helper.
6. Run syntax/config checks, restart only the OpenClaw gateway, and perform real send smokes.

## Verification
Node syntax and config validation passed. The gateway was active. Two real topic sends were logged as plain text sends with the thread id preserved. The post-update helper reported that plain-text delivery was already applied.

## Limitations
- This repair did not prove the unsupported block disappeared on every client.
- On 2026-06-18 the issue reproduced more broadly, including Hermes and additional edit/preview paths; see [P-047](P-047.md).
- Raw bundle names and internal paths are not stable APIs and are not published here.

## Related cases
- [P-045](P-045.md) — progress draft cards were a separate rich path.
- [P-047](P-047.md) — later two-sided Hermes/Talos repair.

## Evidence confidence
**Medium-high for the first repair, medium for full closure.** Server-side smokes were verified, but complete client visual proof and full path coverage came only in later cases.
