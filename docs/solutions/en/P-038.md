# P-038. Hermes → OpenClaw handoff could lose the result when the runner failed

[Русский](../P-038.md) · [Index](../../problem-index.en.md)

**Status:** partially verified: the runner was changed to write a blocked result on failure, but no separate post-change end-to-end failure reproduction is recorded.

## Conditions and symptoms

On 12 June 2026, the Talos/OpenClaw update itself completed successfully and both gateways were active, but a follow-up orchestration task through the runner became slow and opaque. The Talos task runner used Gemini Flash and hit a free-tier quota 429; no result file was written. To a watcher, this looked like a lost task.

## Cause and testable hypothesis

The OpenClaw update was not the root failure. The issue was in the orchestration layer: when the model/CLI call failed, the runner did not materialize the failure as a result. The testable rule is that every task should end with an explicit `status: blocked` or `status: error`, not a missing file.

Generic runner pattern:

```sh
if agent_call_fails; then
  write_result status=blocked reason="model_or_quota_failure"
fi
```

## What helped and what failed

The stale runner was stopped without restarting healthy gateways. The runner was then changed so failed OpenClaw calls write a blocked result, and a `TALOS_TASK_MODEL` override was added while preserving the old default.

What failed was silent waiting: the missing result file turned a clear quota failure into an ambiguous orchestration hang.

## Validation and limits

The record reports `bash -n` OK for the runner script, Hermes and OpenClaw gateways active, and no remaining active runner/agent/update processes after cleanup. Limit: the record does not include a deliberate post-change failure test and readback of the new blocked result, so the status remains partial.

## Evidence

Internal maintenance record “Hermes/Talos Runner Optimization” dated 12 June 2026. Full runner paths, task IDs and raw logs are omitted.
