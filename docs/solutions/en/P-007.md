# P-007. Gateway was active, but Telegram stopped responding

**Status:** partial recovery confirmed; the record does not capture an actual reply to the user’s Telegram message.

**Evidence:** MAINTENANCE note from 2026-06-13; direct observations of service state, gateway logs, and CLI model smoke. Raw logs, private paths, tokens, domains, and addresses are intentionally omitted.

**RU:** [`P-007.md`](../P-007.md)

## Symptoms
Hermes appeared active, but Telegram did not respond. The last workflow ended with a 180-second drain timeout and an empty response.

## Conditions and timing
Linux VPS, systemd, Hermes Agent v0.16.0 / 2026.6.5, 2026-06-13 MSK / 2026-06-12 UTC.

## Hypothesis / root cause
The model CLI smoke worked, so the model path was alive. The failure was in a stale Telegram/gateway layer after an interrupted/restart flow. The root cause of the stuck drain was not established.

## Actions that worked
After checking that no user action was in progress, only hermes-gateway.service was restarted. The old process was killed by systemd after the stop timeout. Talos/OpenClaw, MCP, proxy, and adjacent services were not restarted.

## Verification
The service became active; logs showed Telegram polling and a running gateway; the post-restart CLI smoke returned the expected response.

## Limitations
This is layer recovery at the time of the check, not a proven fix for the drain timeout cause. Without a recorded real Telegram reply, full end-to-end recovery cannot be claimed.
