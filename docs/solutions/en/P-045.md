# P-045. Telegram progress card rendered as an unsupported message

**Русская версия:** [../P-045.md](../P-045.md)

## Status
**Partially verified as of 2026-06-20.** The progress-draft gate was closed and additional rich send/edit paths were later found and closed by server-side checks. The receipt does not contain a screenshot/visual proof from the affected client after all patches.

## Conditions
- Date: 2026-06-20.
- Surface: Talos/OpenClaw → Telegram for macOS during tool calls and slash/system replies.
- Actors: the tool runner creates progress events; OpenClaw streaming/Telegram delivery builds preview/progress payloads; the Telegram client renders them.

## Symptoms
Unsupported progress-draft cards appeared during tool calls even though the previous plain-text repair reported `already patched`. Later, a similar unsupported block appeared on a system/slash-command reply unrelated to tool progress.

## Cause / hypothesis
The plain chat text path was covered, but tools used a separate rich/progress-draft path. A self-restart of the gateway during a tool call could also orphan a progress card. Later investigation found additional generic command/system send and streaming-preview paths.

## Failed sequence
1. The operator sees an unsupported block.
2. The old repair is run, but it checks only the text send/edit path.
3. The script truthfully reports `already patched` for its narrow scope.
4. A separate progress or system/preview path continues sending rich payload.

## Successful sequence
1. Treat text send/edit, progress drafts, command/system replies, and streaming preview as separate paths.
2. Do not treat idempotent `already patched` as proof that every path is covered.
3. Disable tool-call progress drafts until the client compatibility is proven.
4. Find and move remaining Telegram rich send/edit call sites to plain Bot API.
5. Update the post-update helper and verify idempotency.
6. Restart only the OpenClaw gateway after syntax/config checks.

## Verification
- Script syntax and Node syntax passed.
- A runtime import test for the progress gate returned `false` for test tool names.
- Config validation passed, the gateway was active, and the Telegram provider reconnected.
- A later exhaustive sweep found none of the previous Telegram rich call-site markers; the helper reran idempotently.

## Limitations
- There is no final screenshot proof after all repairs.
- Bundle names and call sites change between versions, so the repair must be repeatable and rechecked after updates.
- The separate self-restart-mid-turn problem is not fixed merely by a plain-text patch.
