# P-020. Fallback-цепочка смешивала лимиты, неверный slug и несовместимый payload

**English:** [P-020](en/P-020.md)

**Статус:** частично подтверждённое восстановление. Primary→OpenRouter fallback был приведён в рабочее состояние, но OpenAI direct как общий fallback оставался не доказан из-за несовместимого payload.

## Когда и при каких условиях
21 апреля 2026 Hermes работал с Codex primary и несколькими fallback providers. Primary упирался в usage limit; первый fallback через OpenRouter сначала возвращал 404, затем мог упираться в free-tier 429; второй fallback через OpenAI direct получал HTTP 400 на payload, унаследованный от Codex-style запроса.

## Симптомы
Один инцидент давал разные ошибки:
- primary: HTTP 429 rate/usage limit;
- OpenRouter: 404 на старом slug, потом 429 на дневной квоте;
- OpenAI direct: HTTP 400 `Encrypted content is not supported`;
- ручные тесты иногда: `api_key must be set`.

## Причина
Причины были разными, а не одной общей «fallback сломан»:
1. Codex primary был ограничен квотой, не обязательно сломан.
2. OpenRouter slug устарел или не существовал.
3. OpenRouter free route имеет дневные лимиты.
4. OpenAI API key работал при прямом тесте, но Hermes fallback передавал несовместимый Codex-style payload.
5. `api_key must be set` относилось к ручному процессу без service env, а не обязательно к gateway.

## Роли агента и пользователя
Пользователь видел, что агент перестаёт отвечать при лимитах. Агент должен был разделить среду выполнения провайдера, ручную shell-среду и формат payload, а не менять все ключи и модели одновременно.

## Что не помогало или было рискованно
- Делать вывод о нерабочем ключе по ручному процессу без env.
- Считать `openrouter/free` реальной стабильной моделью: это роутер, модель может меняться.
- Исправлять quota, slug и payload одним большим изменением без промежуточных smokes.
- Печатать значения API keys при проверке env.

## Что сработало
1. Исправили структуру `fallback_providers`.
2. Заменили мёртвый OpenRouter slug на working/free route.
3. Проверили, что при 429 primary происходит переход к OpenRouter.
4. Отдельно проверили OpenAI direct API и доказали, что ключ рабочий.
5. Зафиксировали оставшуюся проблему: OpenAI direct в общей цепочке требует упрощённый payload без Codex encrypted/reasoning fields.

Безопасные проверки:

```bash
python - <<'PY'
import os
print('OPENAI_API_KEY=SET' if os.getenv('OPENAI_API_KEY') else 'OPENAI_API_KEY=MISSING')
PY
# Проверять наличие, не печатать значение.
```

## Проверка результата
Был записан работающий переход к OpenRouter при Codex 429 и успешный прямой OpenAI API response. Но end-to-end OpenAI direct fallback внутри Hermes оставался с HTTP 400, поэтому цепочка была восстановлена только частично.

## Ограничения
OpenRouter free route не гарантирует доступность и качество. OpenAI direct требует отдельной адаптации payload перед тем, как считать его полноценным fallback для Codex-style conversations.

## Основание и уверенность
Основание: lesson «Codex → OpenRouter → OpenAI fallback hardening» от 2026-04-21 и accepted fallback-chain note от 2026-04-27. Уверенность: высокая для диагностики отдельных ошибок; средняя для стабильности OpenRouter; низкая для полной готовности OpenAI direct fallback без дополнительного patch/smoke.
