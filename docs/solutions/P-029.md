# P-029. Google Workspace MCP нестабильно запускался после рестарта

**Статус:** подтверждённый обход на дату проверки; путь к кэшированному entrypoint остаётся хрупким после обновлений или очистки кэша.

[English version](en/P-029.md)

## Симптом
Workspace MCP v1.21.0 мог завершаться или нестабильно подниматься после рестарта при прежней комбинации запуска. Это ломало доступ Hermes/Talos к Google Workspace tools, хотя OAuth credentials и сами аккаунты могли быть рабочими.

## Условия
На VPS сервис `workspace-mcp` обслуживал Google Workspace для Hermes и Talos, включая два аккаунта. Важным требованием было сохранить streamable HTTP endpoint и не смешивать проблему запуска сервиса с OAuth-состоянием конкретного аккаунта.

## Причина или установленный обход
Запись не изолирует единственную причину старого отказа экспериментом. Вместо этого был выбран стабильный запуск через конкретный установленный Python entrypoint Workspace MCP v1.21.0, режим `--single-user`, transport `streamable-http` и `--tool-tier complete`. В Brain canon прямо отмечено, что entrypoint из cache/installed package хрупок при очистке кэша или обновлении.

## Что было сделано
После резервной копии unit/service был закреплён на фактически установленный entrypoint и явные аргументы запуска. Сервис перезапустили, а затем проверили health/MCP initialize и обнаружение инструментов. В дальнейшей записи о hardening адрес прослушивания дополнительно ограничили loopback; см. [P-030](P-030.md).

## Проверка результата
Workspace MCP был active, health endpoint отвечал как healthy, MCP initialize/list-tools возвращал 75 tools. Сквозные проверки подтвердили доступ к двум Workspace аккаунтам без публикации личных данных в публичном кейсе. Поздние регистры фиксируют сервис как active, bound to localhost, с ожидаемыми Workspace tools.

## Ограничения
Обход не доказывает, почему прежняя комбинация аргументов ломалась. Он также зависит от пути установленного пакета: после uv/cache cleanup или package update сервис может потребовать переуказания entrypoint. Отдельные будущие ошибки OAuth/keyring не следует автоматически списывать на этот startup bug.

## Практический вывод
При нестабильном рестарта сначала разделяйте запуск сервиса, HTTP health, MCP initialize/list-tools и account-level read smoke. Успешный list-tools не доказывает доступ каждого API scope, но доказывает, что server process и tool registry поднялись.
