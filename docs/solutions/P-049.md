# P-049. Watcher захватывал служебные файлы вместе с задачами

**English:** [P-049](en/P-049.md)

## Статус
**Не подтверждено как выполненное исправление.** Внутренний урок фиксирует pattern и verification checklist, но найденные записи не содержат адресного diff рабочего watcher и post-change smoke-проверки именно для этой проблемы.

## Условия
- Дата наблюдения: 2026-06-14.
- Контур: Hermes↔Talos Brain inbox watchers.
- Участники: несколько inotify watchers смотрят один inbox; один обрабатывает task, другой result, третий может логировать каждый файл или реагировать на него.

## Симптомы
Один из watchers реагировал на каждый созданный файл в inbox, включая dot/temp/service artifacts и файлы, не являющиеся task или result. Когда несколько watchers следят за одной директорией, это создаёт риск гонок, дублей и неверного определения semantic role.

## Причина / гипотеза
Обработка была распределена по нескольким watchers вместо одного маршрутизатора на inbox. Фильтрация dot/temp/result/frontmatter могла происходить слишком поздно или не в том watcher, что позволяло служебному файлу вызвать побочный эффект.

## Неудачная последовательность
1. Инструмент или редактор создаёт временный или dot-файл в inbox.
2. Inotify watcher видит любой created file.
3. Watcher логирует или запускает обработку без ранней semantic-фильтрации.
4. Возможны дубли, ложные task runs или шумные results.

## Рекомендуемая успешная последовательность
1. Предпочесть один watcher process на inbox directory.
2. Внутри него сразу отбрасывать dot/temp files.
3. Отдельно маршрутизировать `*-result` files в result handler.
4. Перед task handler проверять frontmatter/type task.
5. Перед отключением «лишнего» watcher убедиться, что его полезная роль перенесена или осознанно retired.
6. Выполнить smoke-проверку: real task даёт ровно один result; synthetic result не запускает task; dot/temp file не даёт побочного эффекта.

## Проверка результата
В найденном источнике есть verification pattern: посчитать watchers, проверить enabled service, выполнить smoke-проверку для real task, synthetic result и dot/temp. Записей о выполнении этой smoke-проверки после конкретного изменения не найдено.

## Ограничения
- Не заявлять fixed без receipt с изменённым unit/script и smoke.
- Pattern полезен как runbook, но не как доказательство устранения в production.
- Внутренние paths/logs не публикуются; детали должны оставаться в operational records.
