# P-080. Первую веб-панель требовалось отдельно защитить

**Статус:** подтверждено для майского ремонта. Прямой путь через default host или прямой IP больше не отдавал dashboard, а штатные домены оставались за Access; это не доказывает абсолютную безопасность всех будущих маршрутов.

**Английская версия:** [P-080](en/P-080.md)

## Время и условия
2026-05-24. Проверялись веб-панели Hermes/Talos/OpenClaw на VPS, внешняя граница доступа, состояние SSH, firewall и default host в обратном прокси.

## Симптомы
Обычные доменные адреса были защищены через внешнюю границу Access, но прямой HTTPS-запрос к серверу через default host отдавал HTML Hermes Dashboard с приватным содержимым сессии. Это обходило ожидаемую проверку доступа по имени хоста.

## Подтверждённая причина и гипотеза
Подтверждено: проблема была не в отсутствии Access на доменах, а в том, что альтернативный маршрут через default host или прямой адрес обходил границу по имени хоста. Отдельно обнаружили и исправили избыточно разрешённые настройки SSH.

Гипотеза, которую не надо делать: «если домен защищён Access, всё защищено». Нужна проверка прямых и альтернативных маршрутов.

## Кто что сделал
Оператор сначала сверил канонические записи и политику Access, затем сделал два исправления: ужесточил SSH до режима только по ключу, без root и пароля, и закрыл default host обратного прокси так, чтобы неизвестные HTTP/HTTPS-имена хостов не отдавали панель. Нужные именованные маршруты оставили рабочими.

Что сработало: запрет на default host плюс проверка именованных доменов. Что не делали: не закрывали все 80/443, потому что они нужны для доменной маршрутизации; не ломали существующий порт VPN/transport.

## Практическая проверка
Проверяйте оба направления:

```sh
curl -I https://<protected-hostname>/
curl -k -I https://<server-direct-address>/
ssh -o PreferredAuthentications=password -o PubkeyAuthentication=no <host>
```

Ожидаемо: hostname уходит на Access/login или другую утверждённую границу авторизации; direct/default host не отдаёт dashboard; SSH по паролю не проходит; SSH по ключу остаётся рабочим.

## Доказательство результата
После исправления защищённые hostnames возвращали Access redirect, а прямой HTTP/HTTPS больше не отдавал dashboard content. Проверка также подтвердила работоспособность штатного административного входа и блокировку небезопасного способа входа. Это результаты проверки на дату ремонта, а не описание текущего состояния периметра.

## Ограничения и открытое
Независимый полноценный внешний скан всех векторов обхода не заявлялся; доказан именно майский ремонт default-host/direct-IP. Текущую внешнюю доступность и состояние защитных механизмов нужно проверять отдельно.

## Урок
Защита панели — это не только «домен за Access». Проверяйте default vhost, прямой адрес, открытые порты служб, состояние SSH и сохранение рабочих именованных маршрутов после ужесточения.
