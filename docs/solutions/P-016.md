# P-016. `relogin_required` не всегда означал текущую недоступность модели

**English:** [P-016](en/P-016.md)

**Статус:** подтверждённый результат для инцидента 2026-06-12. Live smoke работал и очистил stale auth error; будущий refresh этим не доказан.

## Когда и при каких условиях
Hermes использовал Codex OAuth route. В auth state уже был исторический `refresh_token_reused`/`relogin_required=true`, а попытка интерактивного device-code relogin во время ремонта получила HTTP 429.

## Симптомы
На уровне state выглядело, что требуется повторный вход. Оператор мог сделать вывод, что модель недоступна, и начать серию новых device-code логинов. При этом реальный минимальный запрос к модели мог ещё проходить.

## Причина или проверяемая гипотеза
Подтверждено расхождение между историческим auth error и текущей runtime-работоспособностью. `relogin_required` отражал записанную проблему refresh-token reuse, но не был достаточным доказательством, что каждый текущий запрос уже невозможен. После успешного smoke stale error исчез из state.

## Роли агента и пользователя
Пользователю нужен был работоспособный агент и уведомление о риске. Агент не должен был бесконечно инициировать OAuth login, особенно после 429. Правильная роль агента — проверить безопасный минимальный runtime smoke, затем поставить alert-only мониторинг, а не автоматический repair loop.

## Что не помогало или было рискованно
- Повторять device-code login после 429.
- Печатать или копировать OAuth-токены для диагностики.
- Считать auth-state flag единственным источником истины.
- Автоматически «чинить» OAuth из cron.

## Что сработало
1. Прочитать только не-секретные поля auth state: provider, error code, relogin flag, timestamp.
2. Выполнить минимальный live model smoke.
3. Если smoke успешен, перечитать state и убедиться, что stale error исчез или больше не блокирует работу.
4. Добавить alert-only watchdog: обнаруживать `relogin_required`, уведомлять, но не запускать login/refresh.

Безопасный smoke-паттерн:

```bash
hermes chat -Q --provider openai-codex -m MODEL -q 'Reply exactly: OK'
# затем проверить state без печати токенов
```

## Проверка результата
Минимальный запрос вернул ожидаемый sentinel. После него `last_auth_error` отсутствовал, `relogin_required` не был установлен. Watchdog dry run показал OK, а alert/recovery send path был проверен как отправляемый.

## Ограничения
Один успешный запрос не доказывает будущий refresh, особенно при rotating tokens. Watchdog только сообщает о новом флаге, но не чинит OAuth.
