# P-018. После обновлений важно различать ошибку настройки маршрута и проверенный smoke

**English:** [P-018](en/P-018.md)

**Статус:** частично подтверждённая история. Майский маршрут Codex был исправлен и прошёл smoke-проверку; сентябрьская запись подтверждает обновление Hermes, но не является отдельным доказательством старого сбоя выбора Codex route.

## Когда и при каких условиях
История растянута между майским post-update repair и сентябрьским обновлением Hermes. В раннем периоде primary route и название провайдера требовали корректировки. Позже Hermes обновлялся уже в другой конфигурационной реальности, с сохранением provider/model настроек и отдельными сетевыми правками.

## Симптомы
В индексе проблема выглядела как «после обновления OpenClaw/Hermes выбирал неверный путь модели Codex». Доступные записи показывают несколько близких, но не идентичных фактов: ранний сбой и исправление маршрута, обновление plugin/runtime, а также успешные smokes в разные даты.

## Причина или проверяемая гипотеза
Подтверждённая часть: неправильный или устаревший provider/model route может пережить обновление и требовать явного smoke именно того route, который считается primary. Неподтверждённая часть: сентябрьское обновление само по себе не доказывает повторение старой ошибки выбора Codex route.

## Роли агента и пользователя
Пользователь ожидает простой вывод «исправлено/не исправлено». Агент должен разделить даты и артефакты: майский smoke проверяет майский fix; сентябрьское успешное обновление проверяет тогдашний gateway и primary response, но не доказывает старую гипотезу автоматически.

## Что не помогало или было рискованно
- Склеивать несколько update receipts в одну причинно-следственную историю.
- Считать `config migrated unchanged` доказательством, что конкретный provider route работает.
- Делать вывод по версии plugin без live request через нужный provider/model.

## Что сработало
1. Перед обновлением сохранять provider/model и fallback contract.
2. После обновления делать явный primary-model smoke.
3. Если предметом риска является Codex route, smoke должен идти именно через Codex provider/model, а не через другой primary.
4. Фиксировать дату, версию и sentinel отдельно для каждого этапа.

Пример безопасной проверки:

```bash
hermes config get model.provider model.default
hermes chat -Q --provider EXPECTED_PROVIDER -m EXPECTED_MODEL -q 'Reply exactly: ROUTE_OK'
```

## Проверка результата
Майская запись подтверждает успешный smoke после корректировки маршрута. Сентябрьская запись подтверждает, что обновление завершилось, gateway работал, модельный ответ вернулся, а конфигурация provider/fallback была сохранена; но она не является отдельной проверкой старого Codex route, если active primary на тот момент отличался или был проверен иначе.

## Ограничения
Статус формулировки «после обновления выбирал неверный путь Codex» остаётся частичным. Для полного закрытия нужна одна запись: до/после config diff, ошибка выбора route, точечная правка, затем live Codex smoke.

## Основание и уверенность
Основание: post-update repair status от 2026-05-23/24, Hermes live update note от 2026-05-24 и Hermes VPS update от 2026-09-16. Уверенность: средняя для майского исправления; низкая-средняя для обобщённой сентябрьской причинности.
