# P-073. Живой бэкенд Hermes не доказывал работу Windows Desktop

**Статус:** подтверждён отдельный урок для Lenovo/Windows Desktop: исправный бэкенд сам по себе не доказывает, что настольный клиент подключён; ремонт требует проверки локального туннеля, задачи и интерфейса.

**Английская версия:** [P-073](en/P-073.md)

## Время и условия
2026-09-27. Lenovo Windows 11 с Hermes Desktop, подключённым к VPS-бэкенду через локальный loopback SSH forward. VPN должен был оставаться включённым; история Task Scheduler на момент расследования не объясняла причину прерывания.

## Симптомы
Бэкенд мог оставаться живым, но Desktop терял связь, потому что локальная Windows-задача или туннель завершались. Пользователь видит не «упал Hermes», а неработающий настольный клиент при потенциально здоровом VPS.

## Подтверждённая причина и гипотеза
Подтверждено: Desktop оставался открыт, когда задача туннеля Windows завершилась с кодом прерывания; перезапуск задачи восстановил локальный прослушиватель и подключение к бэкенду.

Не подтверждено: точная причина завершения задачи. Из-за отключённой истории планировщика нельзя честно приписывать сбой VPN, антивирусу или самому Hermes Desktop.

## Кто что сделал
Диагностика разделила четыре слоя: VPS-бэкенд, локальный SSH forward, запланированная задача Windows/родительский процесс PowerShell и интерфейс Desktop. Принятое исправление оставило один триггер при входе в систему и один долгоживущий родительский процесс PowerShell, который держит один дочерний SSH-процесс с keepalive и перезапускает его после выхода.

Что не сработало как дизайн: триггер с повтором каждую минуту. Его удалили по просьбе пользователя, чтобы не плодить конкурирующие сторожевые процессы и дубли туннеля.

## Практическая проверка
Не считайте `backend /health OK` достаточным тестом Desktop. Проверяйте локально:

```powershell
Get-ScheduledTask -TaskName <desktop-tunnel-task>
Get-NetTCPConnection -LocalAddress 127.0.0.1 -LocalPort <local-port>
```

Затем в Desktop выполните быструю проверку интерфейса: подключение к бэкенду, открытие чата/панели, отсутствие ошибки соединения. Для проверки сторожевого процесса безопасно завершите только дочерний SSH-процесс и убедитесь, что появляется новый прослушиватель, а бэкенд снова отвечает через локальный порт.

## Доказательство результата
В записи подтверждено: после принудительного выхода дочернего SSH-процесса появился новый прослушиватель, ответ бэкенда через локальный forward стал здоровым, подключение Desktop восстановилось. Лишний ежеминутный триггер удалён; принят один входной запуск плюс внутренний цикл перезапуска.

## Ограничения и открытое
Причина первого завершения задачи не доказана. Следующий инцидент нужно начинать с текущего состояния задачи, процессов и прослушивателя, а по возможности — с включённой истории планировщика. Обновление бэкенда и обновление Desktop-клиента — разные кнопки и разные цели; перед обновлением надо определить, что именно обновляется.

## Урок
В архитектуре Desktop с удалённым бэкендом есть минимум два «живых» объекта: сервер и локальный мост. Серверная проверка работоспособности не заменяет быструю проверку интерфейса Desktop и проверку локального супервизора туннеля.
